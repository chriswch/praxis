### Agentic Analytics and Text-to-SQL (natural-language data queries + autonomous insight) · fit 5
*aka / source:* agentic analytics; NL-to-SQL; conversational analytics; Snowflake Cortex Analyst/Agents; Databricks AI/BI Genie; dbt Semantic Layer (MetricFlow)
- **What it is**: lets non-analysts ask questions of data in natural language, with an agent that retrieves a semantic layer, generates and self-corrects SQL, returns the answer, and can proactively investigate anomalies. The 2026 unlock is the semantic layer: metric definitions are pinned in YAML (e.g. dbt MetricFlow) and the agent generates SQL against those definitions rather than improvising them.
- **Use in the process**: treat it as a "get the facts fast" step, not the decision itself — pull the number with an NL question, then still apply your decision criteria as a human. For high-stakes queries, require the agent to attach the SQL it ran and the metric definitions it referenced so you can audit them.
- **Questions to ask**: "What is the exact definition of this metric? Does the agent's SQL match that definition? Did it silently change a join or filter? Is this number strong enough to support the decision I'm about to make?"
- **Engineering**: in a multi-tenant e-commerce backend, define core metrics (GMV, conversion rate, return rate) in semantic-layer YAML and version them in Git so text-to-SQL can't get tenant isolation or timezone handling wrong; force LLM-generated SQL through a read-only account with a row-level tenant filter to prevent cross-tenant data leakage.
- **Product**: when building an "ask your store's data" feature in the admin backend, build the semantic layer first and then attach the agent; never let the LLM hit the production DB directly — route it through a controlled query gateway.
- **Ops**: let ops/CS self-serve questions like "why did this merchant's orders drop last week?" — the agent runs a multi-step investigation and surfaces likely causes, with a human verifying — freeing analysts from repetitive queries.
- **Strategy**: use a cross-warehouse dbt semantic layer to keep metrics consistent across markets and plans, supporting strategy-level comparisons and avoiding teams' metric definitions contradicting each other.
- **2026**: progress is real but warrants caution. Snowflake claims SQL accuracy above 90% on real-world cases once the semantic model is integrated, but academic benchmarks find enterprise-grade text-to-SQL execution accuracy on messy data can be as low as ~31% (Apr 2025), and a LinkedIn internal benchmark reported ~53% correct or near-correct — so semantic layers, self-correction, and human audit remain essential.
- Sources: https://arxiv.org/abs/2507.14372, https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/, https://docs.snowflake.com/en/release-notes/2026/other/2026-04-13-cortex-agents-agentic-analyst, https://datalakehousehub.com/blog/2026-05-semantic-layers-text-to-sql/

### LLM-as-a-Judge · fit 5
*aka / source:* LLM-as-a-judge; model-graded evaluation; pointwise/pairwise/listwise judging; reference-guided grading; meta-judge
- **What it is**: using an LLM to automatically assess the output quality of other LLMs (or products), replacing or supplementing expensive human review. A good judge returns three parts: a score/ranking (Y), a reasoning trace (E — forcing it to explain before scoring improves consistency), and actionable feedback (F). Three modes: pointwise (score one output), pairwise (compare two), listwise (rank many).
- **Use in the process**: turn "is this subjectively good?" into a scalable, repeatable evaluation signal you can wire into CI/CD and A/B tests as a gate — but keep a human in the loop for high-stakes decisions. Do error analysis with domain experts first to define the scoring dimensions, write an explicit rubric, and calibrate the judge against human spot-checks.
- **Questions to ask**: "Am I evaluating the base model, or the whole product wrapped in prompting/retrieval/tools? Is the rubric single-dimensional and reproducible? Does the judge have position, length, or self-preference bias? How well does it correlate with human labels?"
- **Engineering**: in CI, use LLM-as-a-judge for regression testing of AI features (e.g. product-description generation, support replies): every prompt change runs a fixed test set, and the judge blocks the merge if scores fall below threshold; use a different vendor's model for the judge than for the generator to reduce self-preference bias.
- **Product**: when shipping AI features (smart recommendation copy, automated returns/exchange replies), use pairwise comparison of new vs. old output as the launch-decision basis instead of relying only on human eyeballing.
- **Ops**: sample and judge live AI output and track the quality-score trend, alerting when scores drop abnormally (treat the judge as a quality guardrail metric).
- **Strategy**: when deciding whether to adopt an LLM vendor, use a uniform judge plus a domain benchmark to compare cost vs. quality as an objective basis for the vendor decision.
- **2026**: research through 2024–2026 documents significant judge biases: position bias (favoring the first-listed answer), verbosity bias (favoring longer answers), and self-preference bias (favoring one's own output); some studies report frontier models failing 50%+ of bias-probing tests. Mitigations: swap A/B positions and average, reference-guided grading, ensemble/meta-judge, choosing a cross-vendor judge, and ongoing human spot-checks to calibrate for the specific domain.
- Sources: https://agenta.ai/blog/llm-as-a-judge-guide-to-llm-evaluation-best-practices, https://www.adaline.ai/blog/llm-as-a-judge-reliability-bias, https://arxiv.org/html/2410.21819v2, https://arxiv.org/pdf/2410.02736

### AI-assisted experiment analysis and metrics monitoring (automated guardrails + anomaly detection) · fit 5
*aka / source:* automated experiment analysis; guardrail metrics; pre-registration; anomaly detection; AI-powered metrics monitoring (Datadog et al.)
- **What it is**: using automation/AI to speed up and safeguard experiments — pre-register one primary metric and watch the rest as guardrails; use a statistically valid alerting framework to detect guardrail regressions without inflating false positives, and use AI anomaly detection to flag suspicious changes automatically.
- **Use in the process**: ship/ramp decisions follow a single primary metric + pre-registration + guardrail monitoring. AI detects anomalies and does first-pass diagnosis, but ship/no-ship is called by a human against pre-set criteria — avoiding post-hoc selection of which metric or hypothesis to report (HARKing); a fixed analysis plan plus a pre-set stopping rule also blocks exploiting analytic flexibility / optional stopping to push p<0.05 (p-hacking).
- **Questions to ask**: "Which is my primary metric, and was it fixed in advance? Which guardrails must not regress? Is this significant result a real effect, or an artifact of multiple comparisons or a biased experiment? Is the sample or the assignment skewed?"
- **Engineering**: standardize feature flags, guardrail metrics (error rate, latency, crash rate), and automated checks into the experimentation platform; after deploy, monitor guardrails automatically and auto-alert/auto-rollback on regression.
- **Product**: require every feature experiment to declare a primary metric + guardrails (e.g. conversion must not drop, return rate must not rise); the platform automatically runs the t-test/chi-square and produces a readable conclusion for the PM to decide on.
- **Ops**: apply AI anomaly detection to core merchant metrics (GMV, conversion, complaints) to separate seasonal fluctuation from genuine anomalies, attempt to correlate causes, and reduce false alarms.
- **Strategy**: institutionalize experiment discipline as a platform capability so strategic changes across tenants are validated by controlled experiments, building an "experiment before full ramp" decision culture.
- **2026**: 2025 emphasizes automatically detecting biased experiments (e.g. sample-ratio mismatch), AI-driven guardrail monitoring and anomaly diagnosis (such as Datadog's AI metrics monitoring), and standardizing experiment workflows at scale to remove bottlenecks.
- Sources: https://www.datadoghq.com/blog/ai-powered-metrics-monitoring/, https://arxiv.org/pdf/1808.00114, https://www.harness.io/blog/a-b-testing-at-scale-enable-safe-experimentation-for-platform-teams, https://medium.com/@QuarkAndCode/a-b-testing-in-2025-hidden-complexity-costs-mistakes-scaling-experiments-65d17e9f3dcb

### Human–AI Decision Authority Levels: in-the-loop / on-the-loop / in-command (augmentation vs. automation boundary) · fit 5
*aka / source:* human-in-the-loop (HITL); human-on-the-loop; human-in-command; EU trustworthy-AI guidance; augmentation vs. automation
- **What it is**: set the level of human involvement by risk and reversibility: in-the-loop (a human must approve before the system acts), on-the-loop (a human can intervene during or after operation), in-command (a human retains final authority and can override or shut down). This maps to the augmentation-vs.-automation choice: augmentation has AI surface insight/recommendations while a human decides; automation lets the system act on its own.
- **Use in the process**: classify each decision type up front: high-risk/irreversible (refunds, charges, data deletion, cross-tenant operations) → in-the-loop; medium-risk and reversible → on-the-loop + alerting; low-risk and high-frequency → automated but with an audit log. Design "who is accountable and when a human steps in" into the system rather than bolting it on afterward.
- **Questions to ask**: "Is this decision reversible? How costly is an error? Who is accountable when the AI is wrong? Does the human have enough information and time to intervene meaningfully, or are they just rubber-stamping?"
- **Engineering**: tier agentic ops/deploy actions: reads and diagnostics can be automated; restarting services, changing production config, and cross-tenant batch operations require human approval (in-the-loop) and a complete audit trail.
- **Product**: when designing AI features, label automatic vs. advisory clearly: AI applies a change automatically vs. AI gives the merchant a "suggestion, one-click to adopt." Default to augmentation rather than full automation for actions that touch money flow or customer data.
- **Ops**: route AI-generated "action recommendations" (who to promote to, which price to adjust) through on-the-loop: the system proposes, ops reviews and executes, and the outcome is fed back for the model to learn from.
- **Strategy**: make "augmentation-first" a product principle. HBR's 2026 argument is that long-run winners lean toward augmentation (preserving employee engagement and institutional knowledge); decide which processes to automate vs. augment, and communicate the intent clearly to the team so it isn't misread as headcount cuts.
- **2026**: 2026 consensus — Gartner projects that by 2027 half of business decisions will be augmented or automated by AI agents; Deloitte's 2026 report finds 57% of leaders believe employees must be taught to "think with machines." HBR (Apr 2026) notes a perception gap: 81% of executives think their company is doing augmentation, but only 53% of frontline workers agree.
- Sources: https://hbr.org/2026/04/why-companies-that-choose-ai-augmentation-over-automation-may-win-in-the-long-run, https://www.deloitte.com/us/en/insights/topics/talent/human-capital-trends/2026/decision-making-with-ai.html, https://parseur.com/blog/future-of-hitl-ai, https://www.elementum.ai/blog/human-in-the-loop-agentic-ai

### Countering Automation Bias: Trust Calibration / Appropriate Reliance · fit 5
*aka / source:* automation bias; over-reliance/under-reliance; appropriate reliance; trust calibration; XAI explainability; cognitive forcing / nudges
- **What it is**: automation bias is the tendency to accept an automated system's recommendation without questioning it, even when it is wrong. The goal is appropriate reliance — rely on the AI when it is right, rely on yourself when it is wrong — avoiding both over-reliance and under-reliance. Explainability (XAI), trust calibration, and cognitive forcing (nudges) are the mitigations.
- **Use in the process**: alongside each AI recommendation, require a confidence score, the supporting evidence (explainability), and friction when the AI disagrees with the human (ask the user to commit to their own judgment before seeing the AI's). For high-stakes decisions, deliberately add cognitive forcing so the human can't mindlessly click "approve."
- **Questions to ask**: "Am I accepting this because the AI is right, or just because it is the AI? If the AI hadn't given this answer, how would I have judged it? Is this explanation actually helping me judge, or just making me more confident without making me more accurate?"
- **Engineering**: for AI code suggestions / auto-fixes, require a human to read the diff before approving high-risk changes, and show test evidence rather than just a green check; avoid engineers skipping review because "the AI wrote it" (automation bias).
- **Product**: design AI-feature UI to avoid manufacturing over-trust: surface uncertainty, provide sources, add a second confirmation for critical actions; research shows time pressure amplifies automation bias, so don't rush users through high-risk flows.
- **Ops**: for AI auto-insights/anomaly diagnosis, require supporting data and an alternative explanation so ops don't treat the first AI conclusion as settled; track the rate of "AI recommendation adopted but later found wrong."
- **Strategy**: bake appropriate reliance into AI-feature acceptance criteria and risk governance: measure whether human+AI actually beats human-alone or AI-alone (complementarity), not just AI standalone accuracy.
- **2026**: 2024–2026 research finds that naively "putting a human in the loop" can raise adoption while lowering decision accuracy; XAI effects are mixed (some people do worse with explanations), and 2025/2026 work stresses aligning explanations to value and context; there is empirical work on using nudges / cognitive reflection to mitigate GenAI-induced automation bias.
- Sources: https://thedecisionlab.com/biases/automation-bias, https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10857587/, https://www.sciencedirect.com/science/article/pii/S1877050925030042, https://dl.acm.org/doi/10.1145/3581641.3584066

### Causal Decision Diagram (CDD) · fit 4
*aka / source:* CDD; Decision Intelligence Handbook (Lorien Pratt & N. E. Malcolm); Quantellia; Pratt is a transfer-learning pioneer (1993 DBT algorithm; co-edited *Learning to Learn*, 1998, with Sebastian Thrun)
- **What it is**: a visual tool that draws a decision as a chain of cause and effect, using its element types — Choices (levers you control), Externals (uncontrollable inputs you can't change but must account for — the CDD's signature element vs a plain decision tree), Intermediates (mediating variables), Outcomes, and the Goal — connected by Dependencies (arrows). It emphasizes the causal links and ripple effects from action to outcome more than a decision tree does, letting you see the knock-on consequences of a single decision.
- **Use in the process**: for a complex decision, first draw "the levers I control (Choices) + the externals I can't (Externals) → the intermediate quantities they affect → the outcomes I actually care about, and the goal," marking which links are known causal relationships, which are assumptions, and which carry uncertainty. This shifts the debate from "I think" to "what is our assumption about this arrow, and how do we test it."
- **Questions to ask**: "What are the levers I can actually control? Through which intermediate variables do they affect the outcome? Which causal arrow are we betting on but haven't validated?" — making implicit assumptions explicit.
- **Engineering**: when planning a performance optimization or architecture change, draw a CDD: connect "add cache (Choice) → reduce DB load (Intermediate) → p99 drops + cost rises (Outcomes)" so the trade-off and the overlooked side effect (cache consistency) become visible.
- **Product**: when designing a new feature, use a CDD to connect "feature ships → behavior change → North Star metric," marking which links are assumptions that map directly to the experiments you need to run.
- **Ops**: upgrade merchant-churn analysis from a correlation chart to a CDD: which interventionable levers (support, promotion, onboarding) actually change retention, rather than merely correlating with it.
- **Strategy**: for platform-level strategy (e.g. whether to release a plugin to a given plan), use a CDD to lay out the causal chain and risks of "release → adoption / complaints / ops cost → revenue and churn."
- **2026**: in 2025–2026 the CDD is combined with process models, behavior enablers, and decision-centric dashboards, and is positioned as an important new tool for solving the most complex problems; Pratt's blog keeps publishing cases (e.g. the "connecting decisions to data" series).
- Sources: https://www.lorienpratt.com/why-causal-decision-diagrams-are-the-most-important-new-development-in-solving-the-most-complex-problems-and-what-that-has-to-do-with-dogs/, https://www.lorienpratt.com/a-framework-for-how-data-informs-decisions/, https://aicoach.co.za/the-decision-intelligence-process/

### Causal AI · fit 4
*aka / source:* causal inference; causal machine learning; DAGs / causal graphs; do-calculus; interventions and counterfactuals
- **What it is**: using causal graphs and causal inference to answer "what happens if I intervene" and "what would have happened had I not acted (the counterfactual)," rather than purely correlational prediction. It supports experiment design, intervention testing, and scenario simulation, grounding decisions in causation rather than coincidental correlation.
- **Use in the process**: when an A/B test isn't possible or practical (or you only have observational data), estimate intervention effects with causal methods: draw the causal graph and mark confounders, pick the right identification strategy (covariate adjustment, instrumental variables, difference-in-differences, etc.), then estimate the effect and run a sensitivity analysis. Use it to separate "real effect" from "selection bias."
- **Questions to ask**: "Is this correlation or causation? What are the confounders? If I had not done this, would the outcome be different? Do my identification assumptions (e.g. no unobserved confounding) hold?"
- **Engineering**: for performance/reliability attribution — error rate rose after a deploy — use a causal/quasi-experimental design (compare against unaffected tenants or time windows) to distinguish "the deploy caused it" from "natural traffic fluctuation," avoiding a mistaken rollback.
- **Product**: when a new feature can't be A/B tested at full scale (e.g. released only to some plans), use difference-in-differences to estimate the feature's causal effect on retention/GMV.
- **Ops**: upgrade churn/return analysis from correlation to causation: estimate the true incremental effect of "proactive support outreach" on retention, rather than simply observing that customers who got support retained better (they may have been more active to begin with).
- **Strategy**: use causal/lift analytics for marketing-budget and promotion-mix decisions to estimate each channel's incremental contribution, allocating budget to the channels that have a genuine causal effect.
- **2026**: in 2025–2026 causal AI moves toward the mainstream: Gartner-style surveys indicate ~70% of organizations expect to adopt causal methods by 2026 (with roughly 16% in actual use and ~33% experimenting); the market is growing fast; in Jun 2025 DATA POEM launched what it bills as the first Large Causal AI Model (POEM365). Caution: vendor market-size figures vary wildly and should be cited carefully.
- Sources: https://kanerika.com/blogs/causal-ai/, https://www.imd.org/ibyimd/artificial-intelligence/how-causal-ai-can-improve-your-decision-making/, https://martech.org/why-causal-ai-is-the-answer-for-smarter-marketing/, https://acalytica.com/blog/causal-ai-disruption-across-industries-2025-2026

### Uplift Modeling · fit 4
*aka / source:* uplift modeling; heterogeneous treatment effect (HTE/CATE); persuadables; incremental targeting
- **What it is**: estimating the incremental causal effect of an intervention on each individual or subgroup (CATE), so you target only the "persuadables" — customers who act because of the intervention — and avoid wasting effort on those who would have bought anyway (sure things) or whose probability of the desired outcome actually drops when treated — negative uplift / negative CATE, e.g. a win-back contact that reminds a dormant customer to cancel (sleeping dogs). It is a key technique for e-commerce personalization and promotion.
- **Use in the process**: turn "who do I promote / win back / notify" into an optimization problem: estimate each person's uplift and, under a budget/cost constraint, pick those with the highest incremental effect (guardrailed uplift targeting) rather than blanketing everyone or every high-spender with a coupon.
- **Questions to ask**: "Who does this intervention have incremental effect on? Is there anyone whose desired-outcome probability it actually lowers — negative uplift (sleeping dogs)? Am I maximizing conversions, or maximizing incremental profit?"
- **Engineering**: implement uplift scores as the send decision in the push/notification system, adding frequency capping and cooldown periods to handle the bias from repeated exposure; ensure online score computation uses the same features as offline training.
- **Product**: when building a "smart couponing / win-back" feature, replace rule-based logic (e.g. "spend X to get a coupon") with uplift, and quantify for the merchant the "incremental revenue from this batch of coupons."
- **Ops**: evaluate win-back campaigns with uplift-specific metrics (Qini coefficient, uplift curve) rather than ordinary accuracy, and run a sensitivity analysis.
- **Strategy**: frame marketing-budget allocation as uplift optimization: under ROI and brand-exposure constraints, set overall promotion intensity and audience; at platform level this can be a configurable strategy for each merchant.
- **2026**: 2025 industry evidence stresses implementation difficulty: confounding in behaviorally heterogeneous data can overwhelm the model, which estimates more accurately on more homogeneous cohorts; repeated exposure / cooldown introduces correlated-exposure bias. In Dec 2025 a guardrailed-uplift-targeting playbook (combining causal inference + constrained optimization) appeared.
- Sources: https://arxiv.org/html/2512.19805v1, https://causal-machine-learning.github.io/kdd2025-workshop/papers/16.pdf, https://arxiv.org/pdf/2308.09066, https://medium.com/@med.hmamouch99/beyond-churn-models-how-causal-inference-and-uplift-modeling-drive-effective-retention-1ddedbac2f12

### AI Copilot for Product Discovery and PRDs (thinking-partner mode) · fit 4
*aka / source:* personal AI copilot (Tal Raviv / Lenny's Newsletter); ChatPRD; thinking partner; context-rich prompting
- **What it is**: cultivating an LLM into a thinking partner with persistent context rather than a generic tool: give it a role definition (system instructions), upload foundational knowledge (strategy, competitors, customer research, processes), open a dedicated thread per project, and keep context fresh with frequent voice "chat updates." Once it has enough context, even "what's the most important next thing to do?" yields a personalized, useful answer.
- **Use in the process**: use the copilot to accelerate divergence and stress-testing in decisions: have it apply your company's specific frameworks, role-play stakeholders, and treat disagreement as a thinking catalyst — but treat the output as inspiration, not authority, with the final judgment yours.
- **Questions to ask**: have the copilot ask you back, "What context am I still missing to hit this goal?" — use it to generate a list of "questions you should have asked but didn't"; for a PRD, have it surface unvalidated assumptions and missed edge cases.
- **Engineering**: feed the copilot repo conventions, architecture decision records (ADRs), and rules like CLAUDE.md so it aligns design discussions with the existing architecture and helps draft technical specs and RFCs.
- **Product**: use a ChatPRD-style tool to cut a PRD from hours to minutes: talk through what you know, let it structure that into a workable PRD, user stories, and research plan, then review and edit it.
- **Ops**: have the copilot, given a data summary you paste in, help generate hypotheses and a list of follow-up analysis questions, accelerating the path from "seeing the number" to "knowing what to investigate."
- **Strategy**: load strategy briefs / competitive analyses as project knowledge so the copilot can run scenario walk-throughs and rehearse stakeholder conversations as a sparring partner before strategic decisions.
- **2026**: in 2025 this pattern was systematized in Lenny's Newsletter and elsewhere (four steps: Hire → Onboard → Kick off → Put to work); the 2026 direction is dynamic knowledge integration (automatically pulling from PM tools/messages/decision records), team-level shared context (a new hire inherits ~80% of an already-built copilot), and proactive coaching.

### AI Governance Frameworks (NIST AI RMF · EU AI Act · ISO/IEC 42001) · fit 5
*aka / source:* NIST AI Risk Management Framework 1.0 (NIST AI 100-1, Jan 2023) + Generative AI Profile (NIST AI 600-1, Jul 2024); EU AI Act (Regulation (EU) 2024/1689, in force Aug 2024); ISO/IEC 42001:2023 (AI Management System, published Dec 2023) — the three external regimes you map an AI feature against, distinct from the informal in/on/in-command authority tiers in this file (`references/k-ai-augmented-2026.md` → Human–AI Decision Authority Levels)
- **What it is**: Three complementary regimes for governing an AI system. **NIST AI RMF** is a *voluntary* framework built on four functions — **Govern** (the org-wide function that makes the other three repeatable: policy, accountability, culture), **Map** (establish context and identify risks), **Measure** (test/analyze/track risk: fairness, drift, adversarial, output review), **Manage** (prioritize and respond — accept/mitigate/transfer/avoid); its **Generative AI Profile** adds ~12 GenAI-specific risk categories mapped back to those functions. The **EU AI Act** is *binding law* with four risk tiers — **unacceptable** (prohibited, e.g. social scoring, manipulative or untargeted-scraping systems), **high-risk** (Annex III use-cases: hiring, credit, medical devices, etc. — heavy obligations), **limited** (transparency duties, e.g. disclose you're talking to a bot or that content is AI-generated, Art. 50), **minimal** (no obligation). **ISO/IEC 42001** is the world's first *certifiable* AI management-system standard — a third-party-auditable AIMS, the AI analogue of ISO 27001.
- **Use in the process**: This is a *frame*-and-*record* gate that runs **before you build**, not a post-hoc audit. (1) **Classify the risk tier** of the feature (EU AI Act) — is it prohibited, high-risk Annex III, limited, or minimal? (2) **Map the required controls** to that tier *before* writing code: for high-risk that means a risk-management system, data governance, **technical documentation**, **automatic logging/record-keeping (Art. 12)**, **transparency**, and **human oversight (Art. 14)** — the legal mandate behind your in/on/in-command tier choice. (3) Use **NIST AI RMF** (Govern→Map→Measure→Manage) as the operational scaffolding to actually implement and evidence those controls, and **ISO/IEC 42001** if you want a certifiable management system around it. The output is a tier classification + control map attached to the decision record, so "are we allowed to ship this, and what must be true first?" is answered before a one-way-door build.
- **Questions to ask**: "Which EU AI Act tier does this feature fall in — and could it be *unacceptable* (a hard stop) or *high-risk* (heavy obligations) rather than the minimal-risk default we assumed?" "What controls (documentation, logging, transparency, human oversight Art. 14) does that tier legally require, and have we designed them in *before* building?" "Are we a *provider* or a *deployer*, and in which jurisdictions — does the EU Act even reach us?" "Do we map to NIST AI RMF's four functions, and is anyone certifying to ISO/IEC 42001?"
- **Engineering**: Before building an LLM feature that auto-replies to customer messages, classify it (likely *limited-risk* → Art. 50 disclosure that the user is interacting with AI) and wire the controls in from the start: Art. 12-style event logging, a transparency banner, and a NIST-Measure harness (eval set, drift/fairness checks) in CI — rather than retrofitting an audit trail after launch. If the same engine were repurposed for credit decisions, it jumps to high-risk and the obligation set explodes.
- **Product**: A résumé-screening or candidate-ranking feature is **high-risk Annex III** under the EU Act — so the product spec must include human oversight (a recruiter can override, Art. 14), documentation, and logging as acceptance criteria, not nice-to-haves; "ship a minimal-risk MVP" is not an available option for that use-case, and discovering that at launch is far costlier than at frame time.
- **Ops** *(non-software / clinical)*: A hospital deploying a third-party diagnostic model (e.g. reading scans) is a textbook **high-risk** case (medical-device-adjacent, Annex III). Before go-live, ops maps the regime: NIST **Map/Measure** to validate accuracy and bias across patient subgroups, **Art. 14 human oversight** so a clinician confirms rather than rubber-stamps (ties directly to `references/k-ai-augmented-2026.md` → Countering Automation Bias), **Art. 12 logging** for traceability, and possibly **ISO/IEC 42001** certification of the AI-management system — all mapped *before* the model touches a patient.
- **Strategy**: Treat governance posture as a market-access decision: ISO/IEC 42001 certification and a clean EU-tier classification become procurement table-stakes and a B2B trust differentiator. For a roadmap, classify the *whole portfolio* by tier so you know which bets carry a heavy compliance tail (high-risk) versus which are cheap to ship (minimal) — a one-way-door check (`references/c-decision-process-and-governance.md` → One-Way vs Two-Way Door) before committing capital.
- **2026**: The headline change is **timeline relief**: the EU's **Digital Omnibus** provisional agreement (7 May 2026) **postpones high-risk Annex III obligations from 2 Aug 2026 to 2 Dec 2027** (Annex I product-embedded systems to 2 Aug 2028), and adds a new Art. 5 prohibition on AI "nudifier"/CSAM imagery — but this only takes legal effect on formal adoption/publication, expected before 2 Aug 2026, so treat the new dates as provisional. **GPAI obligations have applied since 2 Aug 2025** (legacy models on-market before that date have until 2 Aug 2027; AI Office full enforcement from 2 Aug 2026). NIST RMF and ISO/IEC 42001 are stable. By 2026 a tier classification + control map is becoming a standard pre-ship gate; do not state the postponed dates as final.
- Sources: https://nvlpubs.nist.gov/nistpubs/ai/nist.ai.100-1.pdf, https://artificialintelligenceact.eu/article/14/, https://www.iso.org/standard/42001, https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines-and-other-key-changes/

### Eval-Driven Shipping Gates and Agentic-Workflow ROI (gate AI on evals like tests; pick the cheapest architecture that clears the bar) · fit 5
*aka / source:* eval-driven development; eval gates / CI eval suites; golden datasets; "agents are often overkill" (Anthropic, *Building Effective Agents*, Dec 2024 — workflows vs. agents distinction); inference-time / test-time scaling
- **What it is**: two linked 2026 practices that go past "use an LLM-judge" and "buy a copilot." (1) Eval-driven shipping gate — before you ship or change an AI feature, gate it on a *versioned* evaluation set (golden cases drawn from real production failures + an LLM-as-judge calibrated to humans + pre-registered regression thresholds) exactly the way unit tests gate code; ship/no-ship is a bar fixed in advance, not a vibe check. (2) Agentic-workflow ROI — decide *whether* an autonomous agent is worth it versus a deterministic pipeline or a single LLM call, weighing token/compute cost and latency against value and reliability. Anthropic's guidance: start with the simplest thing, add agentic complexity only when simpler approaches demonstrably underperform, because "agentic systems often trade latency and cost for better task performance."
- **Use in the process**: this is a *decide + record* discipline for AI features. At **decide**, set the pre-registered eval bar (which golden cases, which judge, what threshold) as the go/no-go criterion, mirroring AI-assisted experiment analysis (`references/k-ai-augmented-2026.md`) for runtime metrics. At **frame/options**, run the architecture-ROI choice as a real option set: single call → deterministic workflow → agent, default to the leftmost that clears the eval bar. Record the eval-set version and the threshold in the decision log so a future regression is detectable.
- **Questions to ask**: "What is the pre-registered pass bar, and was it fixed before we saw this candidate's scores? Are golden cases real production failures or self-generated softballs? Does the simplest architecture (one call / fixed pipeline) already clear the bar — what does the agent buy that justifies its token, latency, and reliability cost? Is the judge calibrated to humans, or are we Goodharting (`references/i-ops-analytics-and-metrics.md`) the eval itself?"
- **Engineering**: gate the prompt/model/retrieval pipeline in CI on a Git-versioned golden set; a PR that changes any of them re-runs the suite and the judge blocks merge if pass rate falls below the pre-registered threshold (e.g. <95% on golden cases), treating eval regressions like a failing test — not a reviewer's opinion.
- **Product**: for an "auto-draft support reply" feature, resist shipping a multi-tool agent first; spike a single structured LLM call against the golden set, and only escalate to an agent if the call provably can't clear the quality bar — capturing the cost/latency delta the agent costs to hit the same bar.
- **Ops**: in a clinical-coding or claims-triage workflow (non-software), pre-register the accuracy/recall bar on a labeled gold set audited by domain experts; a vendor or model swap ships only if it clears the bar on that frozen set, so "the new model feels better" can never override a measured regression on the cases that matter.
- **Strategy**: make "simplest architecture that clears the eval bar" a platform principle and use Value of Information / EVPI (`references/a-discipline-and-process.md`) to decide when a decision warrants spending inference-time scaling (deliberate-reasoning models, more sampling) to buy quality with compute versus when a cheap model already suffices — avoiding the trap where 40%+ of agentic projects are reportedly slated for cancellation by 2027 for chasing autonomy nobody priced.
- **2026**: eval-driven development is consolidating into "AI-native CI/CD" — eval gates, prompt-diffing, and canary rollouts as named stages; golden sets are explicitly sourced from production failures, not synthetic data. The agents-vs-workflows critique hardened through 2025–2026: industry analyses report a large share of *failed* enterprise automations used agents where a deterministic pipeline would have been cheaper and more reliable, and only ~11% of enterprises run agentic AI in production. Inference-time scaling (o3-class reasoning models, extended chain-of-thought) is now a real lever to trade compute for quality — but DeepMind/arXiv work shows the win is task-dependent and not yet reliable on knowledge-intensive tasks, so treat "spend more compute" as a sometimes-bet, not a default.

### Multi-Agent Debate / Deliberation and Its Limits (MAD) · fit 4
*aka / source:* multi-agent debate; LLM deliberation; "engineered dissent"; originated by Du, Li, Torralba, Tenenbaum & Mordatch, "Improving Factuality and Reasoning in Language Models through Multiagent Debate" (arXiv:2305.14325, 2023; ICML 2024)
- **What it is**: running several LLM instances that propose answers, critique each other over rounds, then converge — the AI-era instantiation of red-team / devil's-advocate (`references/e-biases-and-debiasing.md`) and groupthink avoidance. The original claim was large reasoning/factuality gains, but 2024–2026 work is sharply qualifying it: most MAD setups fail to beat a single strong model run with **self-consistency** (sample N, majority-vote) at the *same* token budget, and debate often degrades through conformity — minority agents abandon correct answers to match the majority, producing a consensus that *looks* aligned but hides reasoning misalignment.
- **Use in the process**: a divergence amplifier in the options/evidence steps for a contested, hard-to-reverse call — but only if you **engineer the dissent**, because naive MAD multiplies cost without adding signal. Force each agent to answer **independently before exposure** (block information cascades), assign an explicit **dissenter / devil's-advocate** role rather than hoping disagreement emerges, **anonymize** responses to kill identity and position/order effects, and use **cross-vendor model diversity** (different families, not N copies of one). First baseline against self-consistency: if voting N samples of one model wins, skip the debate.
- **Questions to ask**: "Does this beat single-model self-consistency at equal compute, or am I just paying 5x for majority voting? Is convergence genuine reasoning or sycophantic herding? Who is *assigned* to argue the other side, and are answers anonymized and order-shuffled? Are my agents actually diverse, or correlated copies that will agree by construction?"
- **Engineering**: for a contentious architecture call (e.g. event-sourcing vs. CRUD for an audit subsystem), spin up 3 agents from different vendors, collect independent written positions, then run one anonymized critique round with one agent pinned as mandatory dissenter — and capture the disagreements, not just the verdict, into the ADR (`references/f-software-engineering-decisions.md`).
- **Product**: stress-test a PRD or pricing-change rationale by having a "skeptic" persona attack the assumptions before the team meets, surfacing unvalidated bets — but treat output as inputs to a premortem (`references/c-decision-process-and-governance.md`), not a vote that decides.
- **Ops**: when an LLM-as-Judge (`references/k-ai-augmented-2026.md`) pipeline must grade subjective output, an anonymized debate/meta-judge across vendors can reduce single-judge self-preference bias — but monitor that judges aren't converging by conformity rather than agreement on merit.
- **Strategy**: a non-software use — clinical diagnosis: deliberation panels (human or AI) improve accuracy only when independence is protected; the moment one confident voice anchors the room, debate inherits the same conformity failure, so the discipline (independent answers first, assigned dissent, anonymized exchange) is what carries the value, not the deliberation itself.
- **2026**: 2024–2026 evidence is consistently cautionary. Smit et al. ("Should we be going MAD?", ICML 2024) and the ICLR 2025 MAD blogpost find most frameworks fail to surpass self-consistency at matched compute, with model diversity helping only sometimes; Wynn, Satija & Hadfield (2025) document debate rewarding *persuasiveness over accuracy* plus sycophancy and information cascades; Choi, Zhu & Li (2025) show identity/position bias that **anonymization** largely removes (one reported conformity-obstinacy gap fell from 0.61 to 0.02); CONSENSAGENT (Pitre et al., ACL Findings 2025) targets the sycophancy directly. Net: don't deploy MAD naively — engineer dissent or use self-consistency, and pair either with explicit sycophancy guards.
